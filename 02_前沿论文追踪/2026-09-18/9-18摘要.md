## Sol:Pi Recursively Scaling Auto-Research Loops for Efficient Agent Harness

    这个是在Harness上进行改进的项目，原来的coding Agent Harness太烧token，且有过拟合的问题，可以在Harness上加一些机制，减少消耗，机制的来源就是Agent自己想并且自己探索。
所以让代码智能体自己想一些有关减少消耗的“假设”：在编写代码时，xx方法能不能减少token消耗？然后投入沙盒中进行模拟与评估，最终通过多轮任务的实践中，得到真正有效的机制“假设”，这些假设就可以被应用到Harness中，Harness的能力就能得到提升。从验证集（全新任务）的评估结果上看，token消耗能砍一半。

论文里经过筛选得到的有效机制有四个：
1. Action阶段的。以前都是写完代码然后确认（论文背景是无人agent，智能体的确认就是确认修改完毕，一般没用）再执行的，新机制中就可以写完直接在沙盒执行，然后返回测试结果，相当于融合了确认和确认后执行的动作，就不用再专门多交互一次，省token。
    融合有条件的，会判断编辑返回是否成功，是否涉及了破坏性修改，没问题就可以融合。测试的时候也有对Tool Schema改进，消除模型参数写串导致的工具幻觉，以及探索是在隔离环境进行的，随时回传。

2. 上下文压缩阶段的。压缩上下文破坏了前端缓存，可能降低命中率，token消耗就增加了，于是加了个hook，判断压缩后能节省的token费用能不能抵消重写cache的费用，不能就不压缩。

3.  上下文方面的。输出的长文结果会在后续中反复加入prompt，浪费token。于是设立一个门槛，超过门槛的输出就自动移出上下文，存到磁盘，在prompt中把这个输出做个摘要和“超链接”，随时调用，有点类似tool。

4. 日志方面的。编译、测试都会产生日志，大部分没用但是不能随便丢，就把稍微大点的日志给小模型提取recipt，会设立一些护栏，随时能够返回原始日志，确保没幻觉的问题。

## RetireOPD: Self-Retiring On-Policy Distillation for Agentic Reinforcement Learning

    强化学习方向的，针对探索过程中奖励稀疏的问题，奖励稀疏，探索就容易规律；以前的蒸馏过程中，教师也会带歪学生，学生模型始终学习教师模型的效果不理想，也不现实，学生无法超越老师。
核心过程是在策略自蒸馏，原本存在的问题是教师模型也会犯错误，学生模型就训练不好。于是这篇论文加入了“特权机制”，教师模型可以看到特权技能，包括特定任务 参考解法、任务技巧，从而在学生的采样过程中提供对齐监督，让学生把教师的特权技能内化到参数里。
1. 教师模型的构建：用特权上下文+环境奖励+GRPO训练，然后冻结参数。
2. 学生模型：无特权自主采样，GRPO+单样本蒙特卡洛方法逆向KL蒸馏。
3. 蒸馏过程：看两项动态指标，一个是学生模型的对齐进展，一个是学生的能力完备程度，达到一定程度，教师模型就可以退休，学生模型继续GRPO进行训练，避免一直被教师模型压着。

从结果来看，退休方法让学生模型的能力显著提升。
简单而言，这个论文就是通过蒸馏度过前期的稀疏奖励探索阶段，退休解决后期的教师压制阶段。

## ActObs: Don't Mask the Environment: Observation Supervision Changes How Agents Explore Under RL
    以往的工作只监督动作（ActionSFT）,忽略了环境返回的observation（打mask），不计算损失，智能体没有学到环境的变化规律，预测能力极低，就是只会写指令，不能推断指令对环境造成的影响、相应结果等，后果就是探索萎缩与策略探索
这篇论文就是在微调时对环境的observation一并计算语言建模损失，优化的目标函数就是同时包括动作Action和观测Observation（新加），观测加上λ调节权重，这个方法相比其它世界模型，不需要探索新轨迹、没有额外参数、没有增加Prompt、实现难度低。
能够加上终端损失就改变后续轨迹，有个数学原理。动作和观测的梯度会在SFT训练十几步之后“正交”，也就是说这俩东西的参数更新方向是正交独立的，还能达成动态平衡。
原来的Action_onlySFT(理解意思就行)只沿着g_act优化，正交分量也没有，结果就i是act的损失收敛，Observation的损失还是很大；现在的ActObs就是两者协同优化下降，策略稳定改良，抗扰动。
Action_only和ActObs两者的能力差距体现在RL上。在GRPO里，二者的command是一样的，但是ActObs学到环境，策略熵明显大于Action_only，一次你后者针对具体任务通常早早确定策略、固定参数，而ActObs就是在确定著名零的前提下，会遍历所有情况，然后找到最优轨迹。而且ActObs的策略位移相比更小。

从结果来看，这个策略是正确的，而且模型是真的学到了环境因果依赖，即使旧模型提高Temperature，提升也不高。

## EvoSkill-GUI: Reflect, Revise, Reuse: Training-Free Skill Evolution for GUI Agents
    这个主要是在skill层面的，以前的skill是静态的，在复杂环境的变化中依旧呆板固化，这种情况下模型内部也没办法突破局限，另外，不同任务之间的experience不互通。
1. 解决办法是改革skill，skill不再是输入的静态prompt，自顶向下的规划任务路径，在底层操作中加入备选操作、意外处理等算法，这就是鲁棒性来源了，随时可以修改定下来的操作，防止无限循环重复错误操作。
2. 模型反思过程中，也会陷入思维定势，无法迅速且有效找到逻辑链的错误，通常进行检验就是不同模型互查，这篇论文使用的是一个模型，大概就是分割大脑的操作，分出critic用于找出问题，critic被屏蔽了信息，不继承逻辑链，也就不会陷入思维定势，只能看到用户的指令、屏幕上的截图序列、执行的动作序列等，但是看不到之前引用过的skill package，看不到原本的思维链等。这个是合理的，但是以前为啥没听说过呢，我以为很早应该就有了...
3. 于是在处理任务的过程中，即使主计划中无法预料到环境的变化或者不同，模型也能通过可变的skill、tool微调操作，就地修改；就算这样还有失败风险，所以在最外层也加个保障，在可微调的情况下还失败，就通过critic排查，自顶向下，然后记录日志。
4. 这个论文的skill package不容易被检索，因为关键词、高频词啥的容易碰上，于是设计新的检索机制，有点复杂，我就先不研究细节了。
5. 这个可变skill package设计应该比较复杂，而且对于模型的coding能力也有要求，能力弱的模型可能不适用？

## What Does Privileged Information Add to On-Policy Self-Distillation?
    依然是有关On policy Self_Distillation（OPSD），在OPSD中，训练流程基本是“看过privileged message”的教师model监督学生训练。这篇的重点是“Self_Distiilation的提升到底是不是privileged information的功劳？”判定privileged info的边际贡献。
1. 于是这篇论文仅针对privileged info进行对比，将info分为六种不同信息密度，共同解决同一个问题数据集。结果却发现无reference的学生进步幅度和有privileged一样，privileged的边际贡献极小。
2. 对此的解释是Cross-Mode Asymmetry,teacher即使没有privileged info，和学生也存在“不对称”，teacher是thinking的，学生是direct-respond，即使共享参数，thinking模式具有更强的推理能力，因此学生模型本质上还是在学
thinking能力。
3. 论文做了个验证，将学生模型的推理模式改成thinking，distillation的收益直接变负。
4. 这个论文从某种角度上验证了retire的正确性，privileged info的价值有限，学生跨模式学习收敛后，privilege teacher的边际价值已经趋近于0甚至负，而students还能通过RL进步，这时候必须淘汰teacher.

## When EOS Tokens Disagree: Understanding Length Inflation in On-Policy Distillation
    OPD方向。这篇文章的重点是模型的输出长度失控问题。停止的token有很多种，学生和教师学到的可能不是同一种，那么教师模型就会通过惩罚使得学生模型的停止token被停用，而教师模型自己的停止token在学生模型中不适用，学生模型不知道如何停止，于是一直输出，长度失控。
1. 论文里有个比较反直觉的发现：正常思路是让学生和教师模型能够理解彼此的end_token，于是两种思路（第三种就是把所有end_token聚类到一个fix3）
    - 只修decoder（fix1），让decoder学会教师模型的end_token，但是无效；
    - 修老师的分布（fix2），让教师的end_token概率聚到学生的end_token上，有效。
    论文分析decoder方向的修改失效原因：把教师的end_token加进去，概率很低，不容易被采样，反倒是学生的end_token还是一直被惩罚。
2. 论文在三个模型验证观点，认为问题的本质是vocab_table内部的概率分配不同，所以教师和学生可能产生不同的倾向，fix3就可以解决。
3. 论文继续从训练阶段入手：预训练（学生和教师错位）->中训练（学生可以学到教师的end_token，有采样支撑）->SFT（学生偏向教师）->后训练（学生=教师）
    但是论文发现，即使从预训练触发 ，再fix3修复，在训练后期，还是会出现长度膨胀。
    说明程度膨胀不只是EOS的错位问题，在后期存在另一种机制
4.  论文还有一个工程实践上很有价值的附带发现：训练用的 prompt template 和评测用的 prompt template 可以完全独立地影响长度和正确率，两者不必同向移动。
    - 像是DAPO和TTRL两种template，前者将回复要求写在user中，后者将要求写在system中。假设要求是“一步一步推导”，则DAPO倾向于在assistant回复中说更多推理过程，TTRL则是短回答。
    - 而针对上面的独立观点，说的是，即使用DAPO训练，但是最后用TTRL评测，长度也会被压缩，实际推理能力也没有太大变化。
